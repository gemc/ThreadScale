# ThreadScale v1

ThreadScale v1 is the first public release of a language-independent GitHub Action for application
strong-scaling measurements. It runs the same workload over configurable thread counts and reports runtime,
throughput, speedup, and parallel efficiency.

This release includes:

- automatic CPU, affinity, and Linux cgroup-limit discovery;
- single-sweep, thread-sharded, and replicated-sweep execution modes;
- command-template and environment-variable thread configuration;
- repeated measurements, warmups, per-command timeouts, and optional efficiency thresholds;
- CSV, JSON, Markdown, and dependency-free SVG reports;
- a reusable workflow for dynamic matrix fan-out, artifact transfer, aggregation, and plotting;
- rotated replicated sweeps that distribute thread-count ordering effects across runners;
- standard-deviation reporting, per-replica result tables and plots, and prominent CPU topology metadata;
- a standalone `test_scaling` command for running the same measurements and reports outside GitHub Actions.

## Quick start

```yaml
- name: Measure thread scaling
  uses: gemc/ThreadScale@v1
  with:
    command: ./myprogram --threads {threads}
    threads: auto
    runs: 5
    warmup-runs: 1
```

`threads: auto` tests every visible count from `1` through `N`. `threads: powers-of-two`, explicit lists such as
`1,2,4,8`, and inclusive ranges such as `1-8` are also supported and preserve their written order.

Applications that use environment variables can set `thread-env` instead of placing `{threads}` in the command:

```yaml
- uses: gemc/ThreadScale@v1
  with:
    command: ./myprogram
    thread-env: OMP_NUM_THREADS
    threads: powers-of-two
```

## Local command-line runs

The repository-level `test_scaling` script accepts any command containing `{threads}` and produces the same
CSV, JSON, Markdown, and SVG report artifacts as the Action:

```shell
./test_scaling './solver --threads {threads}' \
  --threads powers-of-two \
  --max-threads 64 \
  --duration 60 \
  --strategy replicated-sweep \
  --replicas 3
```

Minimum duration and minimum run-count requirements are both honored for every point. Local single, sharded,
and replicated strategies execute benchmark commands sequentially; replicated sweeps rotate the point order.

## Distributed measurements

The included reusable workflow discovers the runner's available CPUs, creates the required measurement jobs,
uploads each partial result, and merges them in a final reporting job:

```yaml
jobs:
  scaling:
    uses: gemc/ThreadScale/.github/workflows/thread-scaling.yml@v1
    with:
      strategy: replicated-sweep
      threads: auto
      runs: 5
      warmup-runs: 1
      benchmarks: >-
        [
          {
            "name": "solver",
            "command": "./solver --threads {threads}",
            "working_directory": ".",
            "workload": 1000000,
            "workload_unit": "cells"
          }
        ]
```

The three strategies are:

- `single-sweep`: one job measures every thread count for a benchmark;
- `thread-sharded`: one job measures one benchmark and thread count;
- `replicated-sweep`: every replica measures the complete sweep on one runner.

Replicated sweeps report the median of within-runner speedups, preserving paired comparisons while reducing the
effect of hosted-runner variability. Their thread-count order rotates by replica so each count is measured at a
different position in the sweep. Sharded measurements fall back to the ratio of aggregated median runtimes.

## Reports and runner metadata

The final artifact contains `scaling.csv`, `scaling.json`, `summary.md`, and per-benchmark runtime, rate,
speedup, and efficiency plots, plus separate runtime, rate, and speedup curves for every complete replica.
Runtime and speedup plots include ideal-scaling reference lines, and the GitHub Job Summary can render
time-vs-threads, rate-vs-threads, both charts, or neither after each benchmark table. Use the `summary-plots`
input to select the desired summary view. SVG plots use outlined dots for measured points and print each y-value
beside its marker. Summary charts use Mermaid point labels to place the same information directly above the
measured points. Aggregate tables report standard deviation, while expandable tables retain each replica.

Reports record visible, logical, and physical CPU counts; socket and hardware-thread topology; CPU model;
architecture; operating system; runner labels; process affinity; `lscpu` output; and effective cgroup limits
when those values are available.

GitHub-hosted runners are useful for regression signals and functional scaling checks. Stable self-hosted
runners remain preferable for publication-quality performance measurements.

## Requirements

- JavaScript actions must be permitted by the consuming repository.
- The Action uses the GitHub Actions Node.js 24 runtime and has no runtime package dependencies.
- Dynamic job fan-out requires the included reusable workflow or an equivalent caller workflow; a step-level
  Action cannot create additional GitHub Actions jobs after its job starts.

See the [README](https://github.com/gemc/ThreadScale#readme) for the complete input reference, result layout,
benchmarking guidance, and custom workflow integration details.
